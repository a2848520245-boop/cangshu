# M1-架构与计划

> **定稿权**：模块划分、依赖方向、上传七分支、锁与事务、GC 与恢复协议、启动退出码、实施切片以本文件为唯一定稿处。范围以 [[ADR-0001-项目启动与技术栈裁决]] 为准，与 ADR 冲突时以 ADR 为准；字段与约束见 [[06-M1-数据契约]]，接口见 [[05-M1-接口契约]]，运行参数见 [[07-M1-运行手册]]，门槛见 [[08-M1-验收规范]]。
> **性质**：工程契约。只定义「怎么搭、怎么互斥、怎么恢复」，不记录实现状态。全文 UTF-8。

## 1 架构边界与模块

模块化单体：一个进程、一次部署，代码按职责分包，包间靠明确接口交互。模块名与包结构；依赖只能单向。

| 模块 | 负责 | 明确不做 |
|---|---|---|
| `ingest` | 接收上传、流式落临时文件、算摘要（锁外） | 不写最终内容键、不碰数据库表、不做锁与冲突判定 |
| `catalog` | 资源记录与生命周期：写内容／位置／资源行、软删、还原、清空、到期回收、引用计数 | 不做字节读写细节、不做 HTTP 编解码、不做检索实现 |
| `storage` | 内容寻址字节层与并发原语：临时文件、摘要、逐字节比较、移动、幂等删除、分段锁 | 不认识资源业务概念、不写数据库、不做引用计数 |
| `search` | 按文件名、标签、状态的查询（M1 用数据库索引与 SQL 条件） | 不引入独立检索引擎、不做正文全文与语义检索 |
| `job` | 后台任务：GC 回收、到期清空、对账（临时／孤儿／缺失） | 不长驻业务状态、不处理用户请求、不绕过分段锁 |
| `api` | 收发 HTTP、参数校验、错误码映射（M1 不鉴权） | 不直接访问文件系统、不维护第二套业务规则 |
| `web` | Vue 3＋TypeScript＋Vite 界面；构建产物随 Spring Boot JAR 同源提供并调用既有 API | 不新增端点、鉴权、独立服务或第二套业务规则 |

浏览器资源由同一 Spring Boot 进程提供；UI 只调用既有八端点。

## 2 依赖方向与禁令

以下是**业务模块之间**允许的依赖方向（动作向下流，数据向上返）；未画出的反向业务边与循环仍禁止。`catalog → search` 是允许方向，不要求每个实现都出现该引用。

```text
api → ingest / catalog / search
ingest → storage / catalog
catalog → storage / search
job → catalog / storage
storage → 无业务模块（可使用中立的 common 值类型）
```

`common` 是跨包共享的中立值类型与基础处理位置，不承载资源业务状态，也不反向依赖业务模块。`config` 承担运行配置绑定、对象装配与单写者启动门等运行支撑；例如由装配代码将已解析的数据根交给 `storage`，不表示 `storage` 可读取业务配置或反向依赖 `api`／`catalog`。`migration` 执行迁移台账与结构的只读核对，可读取 `config` 的定稿配置；应用入口负责组合 `config` 与 `migration`。这些支撑包关系不改变上图的业务依赖禁令，也不新增独立服务、数据源或架构层。

| # | 禁止 | 替代做法 |
|---|---|---|
| 1 | `ingest` 直接写最终内容键 | 落临时文件 → 交 `catalog` 在锁内移动 |
| 2 | 业务层依赖绝对路径 | 只用相对存储键，路径解析只在 `storage` 内部 |
| 3 | 模块间跨库直连、各建数据源 | 统一数据源，事务由 `catalog` 负责 |
| 4 | `storage` 反向依赖 `catalog` | 判断留在 `catalog` |
| 5 | `api` 直接读写字节 | 一律经 `catalog` |
| 6 | 绕过分段锁直接移动内容键 | 所有触碰内容键的代码都必须在锁内 |

违反禁令的处置：只是分层位置不对 → 记为技术债；破坏不变量（覆盖内容键、绕锁、写绝对路径）→ 停止该路径开发，先补回锁与校验。发现时已产生数据 → 先取证（对账、冲突审计、文件树快照），再修代码，不允许直接删库重来。

## 3 核心不变量与裁决引用

| 不变量 | 裁决出处 |
|---|---|
| 回收站与 GC 口径（软删、保留 7 天、保护引用含回收站行、三段提交、每小时 GC／每日对账） | [[ADR-0001-项目启动与技术栈裁决#^dec-t1]] |
| 并发与锁协议（锁键、六类共锁、单写者启动门、退避与超时） | [[ADR-0001-项目启动与技术栈裁决#^dec-t2]] |
| 迁移台账（版本化 SQL ＋ 只读核对，不符拒启、无降级开关） | [[ADR-0001-项目启动与技术栈裁决#^dec-t3]] |
| 冲突校验前置（先比大小再比字节、移动前、异大小 409、禁止覆盖、不新增冲突态） | [[ADR-0001-项目启动与技术栈裁决#^dec-t4]] |
| 双轨部署（两轨一致项、初始化顺序、禁空库降级、卷与挂载分离） | [[ADR-0001-项目启动与技术栈裁决#^dec-t5]] |
| 门槛四注入矩阵与负对照（四类七点每点 3 次、三快照、全有或全无） | [[ADR-0001-项目启动与技术栈裁决#^dec-t6]] |

三种身份各司其职，不可混用：

```text
内容身份及数据库唯一约束：SHA-256 + 小写 64 位十六进制摘要 + 大小（三元组）
并发锁键及冲突查找条件：SHA-256 + 摘要（不含大小）
物理存储键：sha256/ab/cd/<digest>（ab＝摘要第1–2位，cd＝摘要第3–4位，digest 为小写 64 位十六进制；相对键，不含数据根前缀）
```

**算法命名空间（三处取值，不可合并成一句「同一字符串」）**：① 数据库 `content.hash_algorithm` 与并发锁键使用规范值 `SHA-256`；② 物理路径前缀使用存储命名空间 `sha256`（由 `StorageBackend` 映射，与规范值不是同一字符串）；③ 对外 JSON `hash.algorithm` 维持显示值 `sha256`。任何算法别名（`sha-256`、`SHA256`、`Sha-256` 等）必须先经唯一规范化映射为 `SHA-256` 才允许进入身份与锁；摘要一律小写 64 位十六进制。三处取值不得互相替代，禁止大小写别名绕过锁。

**查询算法（锁内固定顺序）**：先流式落临时文件算摘要 → 取「算法＋摘要」分段锁 → 锁内建立事务快照、按「算法＋摘要」查已有内容 → 先比大小、再比字节 → 无内容记录时检查目标路径存在性 → 持锁至文件操作与事务提交结束。**不得**先按三元组查询、再把「没有完全匹配行」当可新建；若同「算法＋摘要」已存在多条异常记录，拒绝写入并告警，不得任选一条。

## 4 写入与去重协议（七分支）

前置顺序恒定：① 流式落临时文件并算摘要 → ② 取分段锁 → ③ 锁内建立事务快照（`REPEATABLE READ` 的快照**必须在取锁之后**建立，不得先建快照再等锁）→ ④ 按分支处理 → ⑤ 持锁至提交结束。

| 分支 | 条件 | 锁内动作 | 结果标记 |
|---|---|---|---|
| A 新建 | 库内无该摘要，内容地址无字节 | 校验后原子移动（绝不覆盖），插内容＋位置＋资源 | `reused=false` |
| B 命中复用 | 已有该摘要行，大小相同、字节相同 | 不重写字节，只插资源行 | `reused=true` |
| C 复活复用 | 命中行处于非就绪态（含已回收／待回收／回收中） | 先按字节存在／缺失完成校验；字节缺失则重建字节、重建 location 行，再置就绪；**不得只改状态** | `reused=true, revived=true`（`revived` **不对外暴露**） |
| D 大小冲突 | 命中行大小 ≠ 本次大小 | **移动前**拦下；写冲突审计（`SIZE_MISMATCH`）；返回 409 | `CONTENT_CONFLICT` |
| E 字节冲突 | 大小相同、逐字节比较不一致 | **移动前**拦下；写冲突审计（`BYTE_MISMATCH`）；返回 409 | `CONTENT_CONFLICT` |
| F 目标键被占 | 内容地址已有字节，且库内无该摘要行 | 字节相同 → 幂等补齐索引行；字节不同 → 写冲突审计（`TARGET_PATH_EXISTS`）＋ 409 | `reused=true`／409 |
| G 并发抢先 | 移动落空或插入被唯一约束挡下 | 新事务重验字节后转复用；查不到且大小不符 → 409 | `reused=true`／409 |

**事务与失败语义**：字节先落盘，元数据后提交。冲突审计必须在业务事务回滚后仍能保留，采用**独立短事务**或等效可靠写入；审计写入失败应显式报错并留下故障事件，不得返回「审计成功」的结论。冲突时原内容行与物理字节不动，也不新增资源行。

**禁止覆盖**：移动前先查目标是否存在，存在即放弃移动；只允许原子移动或普通移动，**永不使用覆盖式替换**；临时区与正式区必须在同一文件系统，否则失败，不得退化为「复制＋删除」。

## 5 删除、回收与恢复

四段动作，六类操作共用同一把分段锁：

| 阶段 | 触发 | 动作 | 变更 |
|---|---|---|---|
| ① 软删 | 删除资源 | 读资源 → 取锁 → 置删除态、写软删时刻与固定到期时刻 | 只改资源行，引用仍在 |
| ② 硬删 | 到期或显式清空 | 清空须显式确认；仅删除态可清；删资源行后实时查引用数 | 引用数＝0 且非已回收时置待回收 |
| ③ GC 三段提交 | 启动对账后 ＋ 每小时 | 段一：锁内重读状态与引用数 → 置回收中 ＋ 删位置行（独立提交）；段二：幂等删字节（文件已缺＝成功）；段三：置已回收（独立提交） | 状态与位置行 |
| ④ 对账 | 每日 | 临时／孤儿／缺失三类核对与修复 | 只修不一致，不改回收语义 |

**中断续接**：段一提交前被杀 → 保持待回收；段二被杀 → 状态为回收中，字节可能已删或未删，重扫时两种都幂等通过；段三被杀 → 保持回收中，下次 GC 重扫补齐。GC 采用「先元数据、后字节」，方向与上传相反。字节与内容地址不符（`BYTE_MISMATCH`）时**不删除、不置已回收**，立即告警并停止删除。同一对象连续两次每小时 GC 扫描后仍为 `RECLAIMING` 即告警（阈值＝2 个 GC 周期，本轮定稿的初始预算）；启动对账发现残留 `RECLAIMING` 行时立即报告，不等到下一次每日对账。仅「已回收」内容被重新上传时重建字节并复活原行。

## 6 并发与失败处理

**六类共锁**：上传、复用、还原、删除、GC、对账共用同一把分段锁，锁键＝规范值 `SHA-256` ＋ 小写摘要，持锁至文件操作与数据库提交结束。锁内禁止使用锁外快照；GC 决定删字节前必须锁内重读状态与保护引用数。

**取锁顺序**：先非阻塞尝试 → 失败后等 50ms 再试 → 失败后等 100ms 再试 → 最后一次最多阻塞 30 秒；仍失败则拒绝服务并返回 `SERVICE_BUSY`（503，明确可重试），被中断时同样如此。内容唯一冲突回滚后由新事务重试，**重试 2 次**（退避 50／100ms）；字节冲突一律 409，不重试。

**容量与观测预算**：分段锁使用**固定数组 4096 段**，不同摘要落入同段可以串行但不得产生错误的内容冲突；不采用随资源量增长的锁表，也不采用「解锁即移除」。逐字节比较最多 **2 路并行**作为初始运行预算，取得比较名额与分段锁采用统一顺序，等待预算不得层层重置。

**单写者启动门**：DB 会话锁 ＋ 数据根文件锁，两把都要拿到；任一失败即停写，退出码 2，不写任何字节。进程内分段锁不保护跨进程双开，启动门是正确性前提而非优化项。

## 7 状态约束

资源四态与内容六态由数据库 CHECK 强约束，合法转换如下：

```text
resource.status：PENDING → READY／FAILED；READY → DELETED（软删）；DELETED → READY（还原）；DELETED → 硬删行
content.status ：PENDING → READY／FAILED；READY → RECLAIM_PENDING（保护引用归零）；
                 RECLAIM_PENDING → READY（保护引用恢复，引用数>0，回到就绪）；
                 RECLAIM_PENDING → RECLAIMING（段一）；RECLAIMING → RECLAIMED（段三）；
                 RECLAIMED → READY（同内容重传复活）；
                 RECLAIMING → READY（锁内复活：先按字节存在／缺失完成校验，缺失则重建字节并重建 location 行，再置就绪；不得只做状态切换）
```

删除态**不是**删除完成，而是「在回收站里」，行还在、引用还算数。回收中态用于让中断可被下次 GC 幂等接上，**不是冲突态**；不新增冲突状态。

## 8 启动与退出

```text
1) 取 DB 会话锁与数据根文件锁 → 失败：退出码 2，不写字节
2) 只读核对迁移台账：版本集合、脚本名与摘要、关键列类型／非空／外键／唯一／索引、CHECK 与默认值
   → 不符：退出码 3，拒启，无降级开关
3) 完成对账后才允许开始服务
4) 启动后：每小时 GC、每日对账
```

结构漂移的拒启负例至少覆盖：删除 CHECK、放宽状态集合、更改默认值三类。

## 9 实施切片与依赖

顺序建议（链接 [[M1-任务表]] 任务号，不记录进度）：

```text
迁移台账＋结构核对＋单写者门
→ 流式存储＋上传新建/复用/冲突
→ 查询、详情、下载及真实 HTTP
→ 软删、还原、清空
→ GC、对账及中断恢复
→ Compose、恢复、换根
→ 六项门槛＋全量回归
```

| 切片 | 交付物 | 依赖 |
|---|---|---|
| S1 | 迁移脚本与台账、启动只读核对、单写者门、退出码 2／3 | — |
| S2 | 流式落临时文件、摘要、内容寻址、七分支、冲突审计 | S1 |
| S3 | 列表／检索／详情／下载与 `inline=1`、八端点真实 HTTP | S2 |
| S4 | 软删、回收站列表／还原／清空、保护引用实时计数 | S2 |
| S5 | GC 三段提交、到期清空、三类对账、告警出口 | S4 |
| S6 | Compose 交付、重启、备份恢复、换字节根 | S3、S5 |
| S7 | 六门槛与门槛四注入矩阵、全量回归 | S1～S6 |

**计划口径**：任务依赖中「门槛矩阵」是门槛四与门槛五证据的产出方，「文档收口」是最终收口；前置文档工作用独立子项表达，避免出现循环依赖。原任务编号不重排。
